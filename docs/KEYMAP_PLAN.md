# 三键交互与菜单 · 设计方案（方案 B 已实施）

> 状态：**方案 B 已实现并通过编译**（macOS · ESP-IDF v5.5.6 · target esp32c3 · 0 error 0 warning），
> **未上板验证**。实施日期 2026-11-04，固件版本 0.3.0，改动 6 个文件 +399/−32。
> 实施记录见文末「附录 B」。未动 `firmware/`、未碰 `main` 分支、未动协议。
> 适用范围：`passport-fw/main/wb/` 的 WorkBuddy 看板（240×320，UP / OK / DOWN 三键）。

## 0. 一页结论

1. **长按 OK 不能再当菜单键。** 底座电源逻辑在 [main.cc](../../passport-fw/main/main.cc#L171-L180) 的输入任务里独立轮询：按住 OK 到 **2s** 弹「继续按住关机 / 松开取消」，到 **5s** 直接 `power_off`。这段与应用无关，`hold_ok` 只决定 800ms 的 LONG 事件给不给应用，**拦不住 2s/5s**。用户已明确保留「长按 OK 5s 关机」，所以菜单入口改用 **总览短按 OK（当前无待办时）**；根层长按 DOWN 也作为「上一层」的等价入口。
2. **组合键方案不可行。** 三颗键共用同一个 ADC 分压节点（GPIO0），同时按下只会得到一个中间电压，硬件上无法可靠识别「OK+DOWN」。所以不能把关机挪到组合键。
3. **体验差的根因不是某一屏的文案，而是三层缺失**：没有菜单层、没有全局返回层、每屏各自定义按键语义；再叠加长按 OK 被底座占用、长按 DOWN 被赋予不可逆动作。
4. **推荐方案 B（折中统一）**：新增 `SCR_MENU` + `SCR_SOUND`，统一「长按 DOWN = 返回上一层」，只保留审批/提问两个不可逆例外；额度从「长按 UP」迁到菜单；菜单 4 项、无关机。改动只在 `wb_ui.cc/.h` 与 `wb_power.c/.h`（加一个「立即待机」入口），不动协议、不动业务帧。
5. **菜单项**：会话总览 / 额度遥测 / 声音设置 / 待机。**没有关机项**，关机继续由底座长按 OK 5s 负责。
6. **声音设置**只做 40 / 60 / 80% 三档，写 `bsp_audio_set_master_volume()`，**本期不落 NVS**；`settings_set_volume()` 虽已存在且会写 NVS，但它是全局设置、会影响启动器与其他应用，本期不调用（见 §4.6）。

## 1. 体验差的根因诊断

### 1.1 已有的 9 处设计 / 实现差异

| # | 位置 | 设计稿写的 | 代码实际 | 后果 |
|---|---|---|---|---|
| D1 | 总览 OK | 「打开当前会话」 | 有审批→审批页，有提问→提问页，否则无动作（[wb_biz.c](../../passport-fw/main/wb/wb_biz.c#L342-L352)） | OK 有时有反应、有时是死键；用户不知道「当前会话」到底能不能打开 |
| D2 | 额度入口 / 额度返回 | 总览「长按 UP 查看额度」；额度页「UP / OK / 长按 DOWN 返回」 | 入口是长按 UP（与「UP 上一条」同键长按）；额度页**短按 DOWN 无动作**（[wb_ui.cc](../../passport-fw/main/wb/wb_ui.cc#L923-L943)） | 入口靠记；返回有三种写法，其中短按 DOWN 看起来可用其实无效 |
| D3 | 审批长按 OK | 页内写「长按 OK 看全文」 | 长按 OK 被底座占用，没有全文功能 | 设计稿自身矛盾（总说明又说长按 OK 让给底座，见 [index.html](../../docs/ui-design/index.html#L1183)） |
| D4 | 提问长按 OK | 「展开全文」 | 同上，未实现 | 用户按了没反应 |
| D5 | 离线页 OK | 「立即重试」 | OK 只是关掉覆盖页回缓存总览（[wb_ui.cc](../../passport-fw/main/wb/wb_ui.cc#L951-L965)） | 用户以为在重试，实际什么都没做；重连只靠 BLE 自动 |
| D6 | 低电关闭手势 | 正文「长按 DOWN 关闭提醒」，底栏「长按 OK 关机」 | 长按 DOWN 关闭、长按 OK 交底座（[wb_ui.cc](../../passport-fw/main/wb/wb_ui.cc#L967-L979)） | 同屏两套关闭手势，正文与底栏互相打脸 |
| D7 | 待机长按 OK | 一处写「回总览」，一处写「关机」 | 长按 OK = 底座关机；任意短按唤醒（[app_wb.cc](../../passport-fw/main/apps/wb/app_wb.cc#L201-L220)） | 同一页两种承诺 |
| D8 | 长按 DOWN | 全局暗示「返回」 | 审批=直接拒绝（发 `down` 帧）、提问=跳过（发 `skip` 帧）、额度=返回、总览=无动作、离线/低电=关提醒（[wb_biz.c](../../passport-fw/main/wb/wb_biz.c#L389-L421)） | 同一个手势既可能是「退出」，也可能是**不可逆业务决定**，误触代价极高 |
| D9 | 短按 DOWN | 各页都写「选择 / 下一条」 | 总览=下一条、审批=切到拒绝、提问=下移、低电=被屏蔽、离线=关覆盖页并继续翻页 | 在低电页按 DOWN 完全没反应，用户会以为按键坏了 |

### 1.2 三类根因

**A. 每屏各自定义按键语义（D1~D7、D9）**
底栏文案是唯一「契约」，但这张契约每屏重写一次。用户无法形成肌肉记忆，只能读底栏；读完再按，焦点已经变了。更糟的是有些键在某一页是死键（D2/D5/D9），有些键在同一页有两种承诺（D6/D7）。

**B. 缺少层级（D2、D5、D8）**
- **没有菜单层**：额度只能靠「长按 UP」这种隐藏手势进入，进入后也没有「父页面」概念，返回目标靠猜。
- **没有全局返回**：返回在额度页是「UP / OK / 长按 DOWN 三个都行」，在审批页是「答完自动退」，在离线/低电是「任意键消失」。同样是「退」，四套规则。
- **页面没有归属关系**：审批/提问是业务抢占，额度和菜单是用户主动进入，但代码里都只是 `target = ...` 的平铺选择（[wb_ui.cc](../../passport-fw/main/wb/wb_ui.cc#L996-L1008)），没有「谁从哪来、回哪去」。

**C. 长按语义与底座冲突（D3、D4、D6、D7、D8）**
- **长按 OK** 已被底座 2s 提示 / 5s 关机占用；凡是设计稿里承诺「长按 OK 看全文 / 刷新 / 回总览」的功能，全部落空。
- **长按 DOWN** 被当成「返回」，又被审批/提问当成「不可逆动作」。这不是文案问题，是同一手势承担了两种风险等级完全不同的职责。
- **长按 UP** 被额度占用，与短按 UP 的「上一条」形成「按久一点换功能」的隐藏层，正是用户觉得「不可预测」的来源。

## 2. 三键全局语义表

### 2.1 全局固定层（所有页面一致，不随页面变化）

| 键 | 事件 | 全局含义 | 说明 |
|---|---|---|---|
| UP | 短按 | 上移 / 上一条 / 焦点上移 | 纯方向，不产生业务提交 |
| DOWN | 短按 | 下移 / 下一条 / 焦点下移 | 纯方向，不产生业务提交 |
| OK | 短按 | 确认 / 进入当前项 | 具体「进入什么」由当前页决定，但**不会是死键** |
| DOWN | 长按 | **返回上一层** | 根层（总览）= 打开菜单；菜单内 = 关闭菜单；额度/声音 = 回菜单 |
| OK | 长按 | **不归页面所有** | 底座：2s 提示、5s 关机；页面不得承诺任何长按 OK 功能 |
| UP | 长按 | **不承载功能**（本期撤掉额度入口） | 避免「按久一点换功能」；保留给未来调试，不进底栏 |

> 设计原则：**短按只做「移动 / 进入」，长按只做「退一层」**。高风险动作（拒绝 / 跳过）才允许使用长按，并且必须在底栏明写。

### 2.2 页面局部语义（只允许下列例外）

| 页面 | 局部语义 | 为什么必须局部 |
|---|---|---|
| 审批 | 短 OK = 确认当前选项（允许/拒绝）；长 DOWN = **直接拒绝** | 产品明确要求「长按 DOWN 拒绝」；这是不可逆动作，必须在底栏单独标注 |
| 提问 | 短 OK = 提交当前选项；长 DOWN = **跳过** | 跳过是业务动作（发 `skip`），不是导航返回 |
| 待机 | 任意短按 = 唤醒，并吞掉这一次按压 | 防止「唤醒 + 误操作」；不进入任何页面 |
| 离线 / 低电 | 短 OK 或长 DOWN = 关闭覆盖页，回缓存总览 | 覆盖页不是层级节点，关掉即回根 |
| 菜单 | 短 OK = 进入；长 DOWN = 关闭 | 菜单是根层之上的一层 |
| 声音设置 | UP/DOWN = 换档并即时生效；OK = 完成回菜单；长 DOWN = 返回菜单 | 只有三个档位，无嵌套 |

### 2.3 冲突清单与裁决

| # | 冲突 | 裁决 | 理由 |
|---|---|---|---|
| C1 | 长按 OK：菜单 vs 底座 2s/5s | **菜单不用长按 OK**；改用总览短 OK | 底座轮询在 [main.cc](../../passport-fw/main/main.cc#L171-L180) 独立执行，应用拦不住；用户要求保留 5s 关机 |
| C2 | 长按 DOWN：返回 vs 审批拒绝 / 提问跳过 | **保留例外，但只限审批/提问页，且底栏必须写「拒绝 / 跳过」** | 不可逆动作不能藏；其他页一律「返回」 |
| C3 | 短 OK：进入 vs 总览「无待办」死键 | 总览无待办时，短 OK = **打开菜单** | 给菜单一个稳定、可发现的入口，同时消灭死键 |
| C4 | 短 DOWN：移动 vs 低电页屏蔽 | 低电页继续屏蔽 UP/DOWN，但底栏写「屏蔽」 | 覆盖页是通知，不该在下面偷偷翻页；文案必须承认它不响应 |
| C5 | 长 UP：额度 vs 上一条 | **撤掉额度长按入口**，长 UP 不再承载功能 | 「长按换功能」是隐藏层，正是不可预测的来源 |
| C6 | 关机改组合键（原方案 C） | **不可行** | 三键共用一个 ADC 分压节点，同时按下无法可靠区分（见 [PASSPORT_C3_HANDOFF.md](../../docs/PASSPORT_C3_HANDOFF.md#L55-L56)） |

## 3. 屏幕地图

### 3.1 层级树

```
上电
└─ 总览（根）
   ├─ 审批 / 提问（业务抢占，自动弹；答完自动回总览）
   ├─ 菜单（总览短 OK 无待办；或根层长按 DOWN）
   │  ├─ 会话总览（回根）
   │  ├─ 额度遥测
   │  ├─ 声音设置
   │  └─ 待机（确认后立即进入）
   ├─ 额度遥测（旧「长按 UP」入口，本期可保留一个版本做兼容）
   └─ 覆盖页：离线 / 低电（打断当前层，关闭后回总览）
待机不是层级节点，是「空闲态」：任何按键唤醒后回到总览。
```

### 3.2 进出表

| 屏 | 从哪来 | 怎么回 | 返回手势 | 备注 / 例外 |
|---|---|---|---|---|
| 总览 | 上电、所有返回、答完审批/提问 | 根，无上层 | 长按 DOWN 打开菜单 | 短 OK 无待办时也打开菜单 |
| 审批 | 总览短 OK（有待办）或 BLE 自动弹 | 总览 | 答完自动退；长 DOWN = 拒绝（例外） | 拒绝是业务动作，不是返回 |
| 提问 | 总览短 OK 或 BLE 自动弹（优先于审批） | 总览 | 答完自动退；长 DOWN = 跳过（例外） | `ans=0` 时 OK 无动作，长 DOWN 仍可跳过 |
| 菜单 | 总览短 OK / 根层长 DOWN | 总览 | 长 DOWN | 超时 30s 也回总览 |
| 额度 | 菜单「额度遥测」；旧长 UP（可选） | 菜单（从菜单来）/ 总览（旧入口） | 长 DOWN；短 OK 也接受为「返回」 | 本期建议从菜单进入，返回目标就是菜单 |
| 声音 | 菜单「声音设置」 | 菜单 | 长 DOWN；短 OK = 完成 | 超时 30s 回总览 |
| 待机 | 空闲 180s；菜单「待机」 | 任意键唤醒 → 总览 | 短按任意键 | 唤醒的那次按压被吞掉 |
| 离线 | 断连（覆盖任何页面） | 缓存总览 | 短 OK / 长 DOWN | 重连自动消失；审批自动重新出现 |
| 低电 | SOC ≤ 15% 且未屏蔽 | 总览 | 短 OK / 长 DOWN | UP/DOWN 屏蔽；充电后 `low_dismissed` 自动复位 |

### 3.3 统一返回规则

> **长按 DOWN = 返回上一层。** 根层没有上一层，所以根层长按 DOWN = 打开菜单（菜单就是根之上的层）。

例外只有两个业务动作：审批页「长按 DOWN = 拒绝」、提问页「长按 DOWN = 跳过」。这两个必须满足：
- 底栏明确写「拒绝 / 跳过」，不写「返回」；
- 只在对应页面出现，离开页面即失效；
- 不把「拒绝/跳过」解释成导航行为（它是发帧）。

额度页、声音页、菜单、离线、低电全部服从统一返回，不再出现「UP/OK/长按 DOWN 都能退」的三套写法。

## 4. 菜单设计

### 4.1 项列表（4 项，无关机）

| # | 主文案 | 小字 / 动态副标题 | 进入动作 | 选中后 |
|---|---|---|---|---|
| 1 | 会话总览 | `3 条 · 1 运行`（无会话显示「暂无会话」） | 关闭菜单回总览 | 保留总览焦点 |
| 2 | 额度遥测 | `剩余 8,420`（未收到显示「额度未知」） | `credit_open = true` | 打开额度页 |
| 3 | 声音设置 | `当前 80%`（主机静音时「主机静音中」） | `sound_open = true` | 打开声音页 |
| 4 | 待机 | `立即进入待机`（有审批/提问时「有待办 · 不可待机」） | `wb_power_standby_now()` | 立即进入待机 |

菜单项**不出现关机**。底栏不出现「关机」，避免和底座 5s 长按 OK 产生第二套说法。

### 4.2 240×320 布局（沿用 V2 骨架，不新增视觉体系）

```
y=10  顶栏：左「菜单」            右：连接点 + 电池 + 百分比
y=52  ┌─────────────────────────────┐
      │▌ 会话总览                    │  行高 38，间距 8
      │  3 条 · 1 运行               │
y=98  ├─────────────────────────────┤
      │▌ 额度遥测                    │
      │  剩余 8,420                  │
y=144 ├─────────────────────────────┤
      │▌ 声音设置                    │
      │  当前 80%                    │
y=190 ├─────────────────────────────┤
      │▌ 待机                        │
      │  立即进入待机                │
y=228 └─────────────────────────────┘
y=274 三键栏：UP/DOWN 移动 | OK 进入 | 长按DOWN 关闭
```

- 行：`x=12, w=216, h=38`，间距 8；4 行占 176px，从 52 到 228，底部留 46px 空隙。
- 焦点：**6px 薄荷竖轨**（`x=12, w=6, h=38`）+ `#0E0E0E` 实心块 + 主字 `#FFFFFF`；非焦点无竖轨、无块、字 `#A8A8A8`。
- 字号：主文案 16px（`buddy_font_16`），副标题 12px（`wb_font_12`）。不引入图标资源，**竖轨就是 V2 的「图标位」**。
- 不改现有 SAFE_L=12、HEADER_Y=10、FOOTER_Y=274、`KEY_W={82,58,72}` 等常量。

### 4.3 焦点与开合手势

| 操作 | 手势 | 行为 |
|---|---|---|
| 打开 | 总览短 OK（当前无审批/提问） | 菜单打开，焦点回到第 1 项 |
| 打开（等价） | 总览长 DOWN | 同上；符合「根层向上」 |
| 移动 | 短 UP / DOWN | 焦点上下循环（4 项首尾相接） |
| 进入 | 短 OK | 执行当前项；除「待机」外都是切屏 |
| 关闭 | 长 DOWN | 回总览，不重建任何页面 |
| 关闭 | 选中「会话总览」+ 短 OK | 同上 |

打开/关闭都用 `lv_screen_load()` 切换静态屏，**不清屏、不 `lv_obj_clean`**：总览、额度、声音的控件常驻，切换无闪烁；数据仍由 1s tick 的快照刷新。

### 4.4 超时与恢复

- **30s 无按键**：菜单关闭回总览；额度、声音同规则（声音回总览，不逐级回菜单，减少状态）。
- 超时计时用 `lv_tick_get()`，不依赖主机 `clock_s`（断连时墙钟不前进，会卡死）。
- 打开菜单算一次活动，会重置 `wb_power` 的 180s 空闲计时；但菜单 30s 自己会先关，不会把「菜单常驻」带进待机。
- 菜单被更高优先级（审批/提问/离线/低电）打断时：**直接关闭，不恢复**；下次打开焦点回到第 1 项。理由：中断意味着上下文已变，恢复旧菜单只会遮挡新待办。
- 从菜单进入额度/声音后，若被审批打断，额度/声音关闭，答完回总览；**不回到菜单**（避免「刚答完又被菜单挡住」）。

### 4.5 额度入口取舍

| 做法 | 优点 | 代价 |
|---|---|---|
| 撤掉「总览长按 UP」 | 消除隐藏手势；额度只有一个父亲（菜单），返回规则唯一 | 老用户需要重新学一次；发现性靠菜单 |
| 保留一个版本的兼容入口 | 不打断当前习惯 | 额度有两个父亲（菜单/总览），返回目标要按来源记，正是「不可预测」的来源 |

**建议**：菜单上线后保留一个构建周期的长 UP 兼容入口，返回仍回总览；下一个构建撤掉。最终只保留菜单入口。

### 4.6 声音设置

- 三档：**40% / 60% / 80%**；默认读 `bsp_audio_get_master_volume()`，不在三档时吸附到最近档（通常 80%）。
- 移动焦点即 `bsp_audio_set_master_volume(档位)` 并播放 `WB_SFX_KEY` 试听；短 OK = 完成回菜单；长 DOWN = 返回菜单（已生效的值保留）。
- **不落 NVS**：`settings_set_volume()`（[settings.cc](../../passport-fw/main/launcher/settings.cc#L345-L360)）确实存在且会写 NVS，但它是**全局设置**，会同时改变启动器、收音机、小智等所有应用的主音量；本期不调用，避免「在看板里调音量，把别的应用也改了」。重启后由 `settings_bootstrap()` 恢复 NVS 值（默认 80%）。
- 主机静音（`beep_vol <= 0`）时，页面显示 12px「主机静音中」；本地档位仍可调，但不会出声，需主机解除静音。
- 不提供 0%（静音）：`bsp_audio_set_master_volume(0)` 会让全局反馈全部失效，属于电源/系统级动作，不应藏在看板菜单里。

## 5. 打断优先级

### 5.1 判定树（从高到低）

```
1. 待机：仅当「无 RUNNING、无审批、无提问」且空闲 180s → 待机
2. 离线：未连接 → 离线覆盖页（即使有审批也显示离线）
3. 审批 / 提问：已连接且有待办 → 审批/提问页（提问优先于审批）
4. 低电：SOC ≤ 15% 且未屏蔽 → 低电覆盖页
5. 菜单 / 额度 / 声音：用户主动层
6. 总览
```

说明：
- **离线高于审批**：断连时审批/提问的 `key` 帧发不出去（`wb_link_send` 会失败），让用户「答了但没生效」比不让答更糟。离线页应加一行「待办 N 条 · 连上主机后可处理」，重连后审批自动重新出现（`s_approval_auto` 仍为 true）。
- **审批高于低电**：低电页只是提醒，不阻断上行；当前实现把低电排在审批之前（[wb_ui.cc](../../passport-fw/main/wb/wb_ui.cc#L996-L1008)），会让待办被一块电池图标挡住，建议调整。
- **待机不会和审批共存**：`wb_power_set_busy()` 在有审批/提问/RUNNING 时禁止进入待机；来审批时 `wb_power_note_activity()` 会立即唤醒（已实现，见 [app_wb.cc](../../passport-fw/main/apps/wb/app_wb.cc#L49-L82) 与 [wb_power.c](../../passport-fw/main/wb/wb_power.c#L105-L153)）。

### 5.2 被打断后怎么恢复

| 被谁打断 | 菜单 | 额度 | 声音 | 恢复位置 |
|---|---|---|---|---|
| 审批 / 提问 | 关闭 | 关闭 | 关闭 | 答完回总览；**不恢复**被关掉的层 |
| 离线 | 关闭 | 关闭 | 关闭 | 重连后回总览；不恢复 |
| 低电 | 关闭 | 关闭 | 关闭 | 关掉低电后回总览；不恢复 |
| 待机 | 已关闭（待机前会先超时） | 关闭 | 关闭 | 唤醒后回总览 |

原则：**瞬时层一律不恢复**；只有「总览的会话焦点」这种持久状态保留。这样任何打断都不会把用户重新塞回一个已经过期的菜单。

### 5.3 待机时来审批

已实现：`apply_approval_locked()` 置 `WB_WAKE_APPROVAL` → `on_biz_change()` 调 `wb_power_note_activity()` → 背光 100%、BLE 正常档、渲染周期恢复 → 下一 tick 显示审批页。设计上确认这条链不变；菜单/额度/声音在进入待机前必须先 `menu_open/credit_open/sound_open = false`。

## 9. 风险与明确不做

**风险**
- 总览短 OK 从「打开待办」扩展到「无待办→菜单」，会改变一个已形成的习惯；需要底栏同步改成「菜单」而不是「无待办」。
- 根层长 DOWN 开菜单与「长 DOWN=返回」共用手势；如果用户从菜单里长 DOWN 关闭，再在总览长 DOWN 又打开菜单，会形成「长 DOWN 循环」，但这是层级树的自然结果，底栏可不提示。
- 声音设置改的是**全局主音量**，会影响其他应用；本期不落 NVS，但运行期仍是全局的，需要在文案上说明「全局音量」。
- 离线优先于审批：如果用户坚持「断连也要看审批内容」，需要把离线页做成「可查看、不可提交」的降级审批页，属于后续扩展。

**本期不做**
- 不实现长按 OK 菜单（底座占用）；
- 不实现组合键关机（单 ADC 节点不可行）；
- 菜单不设关机项；
- 不改协议、不改 UI 视觉骨架、不改 `firmware/`、不碰 `main` 分支；
- **已编译通过，但未烧录**：实机回归（见附录 B 清单）留给下一轮上板。

### B.6 上板才暴露、已修掉的两个 P0

**① 分区表不匹配 → 启动失败**

设备原厂分区表 factory 只有 `0x400000`（4 MB），工程 `partitions.csv` 是 `0x7f0000`（7.94 MB）。0.3.0 镜像 4,251,504 B 超出 4 MB，bootloader 报 `Image length ... doesn't fit in partition length 4194304` 并无限重启。
处理：把工程 `partition-table.bin` 烧到 `0x8000`（3 KB），app 与 `0x0` bootloader 未动。
代价：原厂 `cardid`(0x410000) / `storage`(0x420000) 分区不再声明，`cardid` 区域被 app 镜像覆盖；工程 `partitions.csv` 本来就声明不用这两块。
回退镜像：`passport-fw/.tmp/flash-backup-20261105/partition-table-orig.bin`（原厂分区表）与 `app-0.2.0-rc56.bin`（rc56 app）。

> `partitions.csv` 顶部「只写 factory 区段，不动 0x0 bootloader 与 0x8000 分区表」的注释，前提是设备**已经刷过工程分区表**。对原厂板首次烧录必须连分区表一起写 —— `build-mac/flash_args` 本来就是 bootloader + 分区表 + app 三件套。

**② 堆耗尽 → 开机即 panic**

现象：WB 应用启动后 `free heap = 3296 B`，首次渲染进 LVGL `recolor_only()` 时 `lv_malloc()` 失败触发 `LV_ASSERT_MALLOC` → `Guru Meditation Error (Breakpoint)` → 无限重启。
根因：9 个屏各自 `build_header()` + `build_footer()` 建了一整套顶栏状态簇与三键底栏（每屏约 17 个 LVGL 对象，合计 150+）；方案 B 新增 `SCR_MENU` / `SCR_SOUND` 两屏把堆推过临界点。
修复：`wb_ui.cc` 新增 `build_chrome()`，把顶栏 + 底栏改为挂在 `lv_layer_top()` 的**一组共享对象**；每屏文案存进 `hdr_l/hdr_r/key_k/key_a` 字符数组，切屏时 `apply_chrome(target)` 写入。`build_header()` 返回的两个指针指向共享 label，所以 `update_*()` 里原有 `set_text(s_ui.*_idx, ...)` 全部不用改；`wb_ui_deinit()` 单独删共享容器。
效果：`Initial Free Heap: 36 KB`（原 3.2 KB），单次启动、无 panic，实机截图确认视觉无变化。

#### B.7.2 为什么新开一条帧，而不是扩 `status_list`

`status_list` 实测最坏 488 B（设备 512 B 上限、主机按 480 B 告警），源码注释已写明「塞不下 models 数组」。往里加字段会让整帧被丢弃。所以：

- 沿用已有的 `usage` 帧，设备端从「只识别不解析」改成解析 4 个字段；
- Web 独有的网关 / 连接信息用一条约 100 B 的**无 type** `host` 帧，与 usage 同频（30s）；
- 新增 caps **bit6** `WB_CAP_HOST_DASH`（0x40）。设备 hello 声明 `caps=0x43`，主机只在设备声明该位时推 `host` 帧 —— 旧固件（0x3）不会收到不认识的帧而回 `ERR_JSON`。主机端 bit3/4/5 已被「总数语义 / 自动切页 / 语音上行」占用，故用 bit6。

#### B.7.3 交互与代价

- 新增 1 屏只用约 2 KB：`Initial Free Heap 36 KB → 34 KB`（共享 chrome 之后）。继续加屏要重新盯这个值。

### B.8.6 提问页选择交互（2026-11-05 22:40 改，22:45 实机通过）

原实现是「短 OK = 下项、长 DOWN = 提交」，与设计师稿一致但反直觉，且确认后
立刻切页、用户看不到提交了什么。现改为通用选择器语义，**业务层 / 协议 /
主机端一行未改**，只动 `wb_view.c` / `wb_view.h` / `wb_ui.cc`。

| 项 | 行为 |
|---|---|
| 切换 | `↑` / `↓` 移动游标；业务层 `wb_biz_move()` 钳制在 `[0, n_opts-1]`，**不绕回** |
| 确认 | `OK` 确认当前项，上行 `ask_index` |
| 跳过 | 长 `DOWN` 沿用业务层 `wb_biz_back()` → `key="skip"` |
| 长 `OK` | 不消费，留给底座「2s 提示 / 5s 关机」 |
| 选中态 | 琥珀实心底 + 反白字（沿用原风格），新增**左侧 2px 深色光标条**，切换时随选中移动 |
| 切换反馈 | 页脚右段实时显示序号 `N/M`（如 `↑↓ 切换 2/4`） |
| 确认态 | 落选项整行转鼠尾草绿 `WD_SUCCESS`、其余项压暗，页脚变绿字「已提交 · 选项 2/4」；停留 3.5s 后才上行并回总览 |
| 撞首/末项 | 页脚两段转琥珀，右段显示「已到首项」/「已到末项」，3s 后恢复；游标不会卡死 |
| 无选项 | 选项行全部隐藏，页脚红字「暂无选项 · 等待主机下发」，`OK` 不提交（业务层另有 `n_opts > 0` 兜底） |
| 重复确认 | 进入已提交态后 UI 层锁键，第二次 `OK` 被吞，不会二次上行 |

**为什么停留 3.5s**：UI 重绘由 1s 的 `lv_timer` 驱动，按 OK 后首帧落在 0~1s
之间；停留太短会出现「确认了一闪就回总览」，用户看不到提交结果。3.5s 是
「首帧最晚 1s + 可读 2.5s」的下限，再长就嫌拖。

**为什么「先画后发」而不是立即上行**：`wb_biz_confirm()` 会立刻把页切回总览，
先调用就等于把确认态吞掉。现在由 `wb_ui_sync()` 末尾的 `ask_after_sync()`
统一处理：至少渲染一帧（`drawn`）且超过 HOLD 才真正调 confirm。

**实机验证**（`POST /api/test-ask` 注入 4 选项单选，0 error / 堆 56 KB）：
初始 `1/4` → `↓` 到 `2/4` → `↓↓` 到末项 `4/4` → 再 `↓` 显示「已到末项」→
`↑` 显示「已到首项」→ 再 `↓` 游标正常回到 `2/4` → `OK` 后 B 行转绿、
页脚「已提交 · 选项 2/4」→ 回总览。连续按两次 `OK`，设备侧只有 **1 条**
`提问作答 id=22 index=1`，重复确认未二次上报。

**未验**：`n_opts = 0` 的空选项分支（`/api/test-ask` 固定发 4 项，缺注入通道），
仅静态确认代码路径。

**踩坑（写脚本时记住）**：① 打开串口会让 ESP32 复位一次，BLE 要十几秒才
重连；这段时间 `POST /api/test-ask` 会**返回 `ok:false` 但 daemon 日志仍记
「已下发（成功）」**，帧实际送不到设备 —— 必须等链路稳定再发，且不要因为
返回值 false 去重试（重试会连发多道题，把设备反复打回第 1 项）。② 主机对
同一道题每 30s 保活重推，重推会把设备游标重置为 0，长序列验证要分段。

### B.8.7 今日消耗页：模型明细为空（2026-11-05 23:10 修，当日实机通过）

**现象**：今日消耗页「模型用量」卡片只有一行小标题「今日暂无模型数据」，
下面 5 行进度条位置一片空白，卡片像没渲染完。

**根因不在主机**。主机 `host/wb_app.py` 一直在发完整明细：

```json
{"usage":1,"today":860898,"req":10,"cache":...,
 "models":[{"n":"hy4-free","v":461024,"hit":...}, ...]}
```

断点在固件解析层 —— `wb_proto.c` 只取了 `cJSON_GetArraySize(models)` 存成
`usage_models`（一个计数），**`n` / `v` / `hit` 三个字段从头到尾没读过**。
于是 `wb_state_t.usage.model[]` 永远是全零，`wb_ui.cc` 里还有一行硬编码
`s_st.usage.n_model = 0`，视觉层的 5 行循环必然全部走 else 分支。

### B.8.8 试听提示音失效 + 重连补推 cfg（2026-11-06 00:40 修，实机通过）

**现象**：控制台点「试听」按钮，`/api/test-beep` 返回 `ok:true`，设备却不出声。

**根因：JSON 类型不匹配，不是链路问题。**

| 侧 | 行为 |
|---|---|
| 主机 `wb_app.py:_send_beep_cfg` | 落帧 `{"type":"cfg","beep_vol":100,"beep_test":1}` —— **数字 1** |
| 固件 `wb_proto.c` | `ev->beep_test = cJSON_IsTrue(...)` —— `cJSON_IsTrue` 只认字面量 `true`，对 `cJSON_Number` **恒返回 false** |

于是 `s_test_beep` 从不置位，`wb_biz_take_test_beep()` 恒 false，
`app_wb.cc` 的 `wb_audio_play(WB_SFX_CONNECTED)` 分支永远进不去。
主机已成功写出帧、设备也回了 `OK_CFG`，所以从日志上完全看不出异常。

**为什么只有这条固件线坏**：`firmware/main/wb_proto.c` 用的是自研
`wb_json_bool()`，`WB_JSON_NUM` 分支返回 `num != 0.0`，数字 1 一直是 true。
移植到 passport-fw 时换成 cJSON 的 `cJSON_IsTrue`，语义被悄悄缩窄了。
同一个 `wb_app.py` 里 `_build_host_frame` 的注释早就写过「设备固件用
cJSON_IsTrue 解析 secret/cli，所以必须发 JSON bool，不能发 0/1」——
`beep_test` 漏了这条约定。

**修法（两端都改）**：

| 文件 | 改动 |
|---|---|
| `host/wb_app.py` | `beep_test: 1` → `beep_test: True`，与 `secret`/`cli` 约定对齐；老固件的 `wb_json_bool` 也认 true，不退化 |
| `passport-fw/main/wb/wb_proto.c` | 新增 `json_bool()`，兼容 bool / 非 0 数字 / `"1"` / `"true"`；cfg 分支改用它。**即使主机没重启、仍在发数字 1，试听也能用** |
| `passport-fw/main/wb/wb_biz.c` | cfg 处理加一行 `提示音配置 vol=%d test=%d` 日志，现场能直接区分「补推」和「试听」 |

**「重连自动下发」的行为澄清**：`_device_watch_loop` 用连接代次判重，
每次新链路只补推一帧 `cfg`（`_push_beep_cfg`，**不带 beep_test**），
目的是把 PC 侧持久化的音量写回设备（设备不落 NVS，断电回默认 100）。
它本来就**不该响**。实测复位后拿到 `test=0`，符合预期。

**实机验证**（`fw 1.3.0-passport` / 0 error，日志证据）：

```
[复位 → BLE 重连]
I (10658) wb_biz:   提示音配置 vol=100 test=0        ← 自动补推，不响
[点试听 ×2]
I (40961) wb_biz:   提示音配置 vol=100 test=1
I (41267) wb_audio: 播放 CONNECTED: 4160 帧(260ms), 累计 played=2
I (45161) wb_biz:   提示音配置 vol=100 test=1
I (45459) wb_audio: 播放 CONNECTED: 4160 帧(260ms), 累计 played=3
```

`played` 单调递增证明不是「收到帧但没播」，且试听可重复触发。

**注意**：host daemon（PID 4713）本次**没有重启** —— macOS 蓝牙 TCC 权限要求
由 GUI 终端启动，从后台 shell 拉起会 `TCC_CRASHING_DUE_TO_PRIVACY_VIOLATION`。
所以本次实测走的是「主机发数字 1 + 新固件兼容」这条路径；主机侧改成
`true` 的改动要等下次正常重启才生效，届时固件同样认得。**不重启也能用。**

**验证脚本**：`/tmp/wb_verify_beep.py`（RTS 脉冲强制复位制造真实重连，
再两次 POST `/api/test-beep`，比对 `test=` 标记与 `played` 计数）。

### B.8.9 城市电台列表页烧录实机：3 个问题（2026-11-07 00:05，全部通过）

`8878c86` 当初只做了编译/单测/字库验证、没烧录。本轮烧录后用串口抓屏发现
并修掉 3 个问题，其中 1 个是会让设备复位的 P0。

**① 列表页两行文字压叠（P1）**
`buddy_font_16` 的 `line_height = 20`，原实现却把两个 label 显式压成 15px
（第一版改 18px 仍重叠）、行框只有 34/38px，字形画到框外必然上下叠。
改为**不设 label 高度**（自适应 20px）、行框与行距都取 40px，两行正好铺满。
顺带：无数据时隐藏多余空行框、两条功能行移到列表区中部；断网时页脚不再
显示误导性的「稍候」，改成可操作的「确定切换  长按下返回」。

**② 进入列表页后 OK 落到「返回主屏」（P1）**

`on_key` 的列表分支统一按 `shown + 2` clamp，两层共用同一个上界。

`catalog_worker` 在 `radio_catalog_discover_location()` 之前用
`radio_catalog_network_ready()` 判断，无网直接落空态返回、不碰 lwIP；
同时补 `radio_app_start()` 里「启动时 WiFi 已连接」分支遗漏的
`s_wifi_connected.store(true)`，否则有网设备会被误判为无网而跳过查询。
新 hook 定义在切片之外，`test_radio_lifecycle.py` 补 mock 恒 true，
